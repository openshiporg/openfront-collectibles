- **URLs:** `/us/checkout?step=payment`, `/dashboard/platform/orders/create`
- **Steps:**
  1. **Storefront:** add 1881 Silver Dollar, check out with the address QA Round2, 1 QA Street, Austin TX 78701, and choose "Tracked shipping $18.00".
  2. **Admin:** Create order → 1881 Silver Dollar → customer QA Order → address → **Create Cart**.

- **Actual:**

  - `regions` shows both regions with `pp_stripe_stripe` (`isInstalled: true`) and `pp_system_default` attached:

- **What's needed (the fixer can't do it alone):**

  - **And/or** a product decision to let the **admin** record a paid offline sale: bank wire or in-person, the normal way a $3,000–$5,000 collectible is paid for. E-commerce has the same rule, so this is a vertical-level choice.
- **Files:** `features/keystone/queries/activeCartPaymentProviders.ts:33-39`, `features/keystone/mutations/completeActiveCart.ts`, `features/platform/orders/screens/OrdersCreatePage.tsx`, Railway env.
- **Impact:** order confirmation, order history and detail, admin order detail and fulfil, High-Value Fulfillment, invoices and analytics with sales are still untestable on real data. This is the third round in a row.

## Major

### QA-035: Admin customer picker still finds nobody when you type
- **Area:** dashboard
- **URL:** `/dashboard/platform/orders/create` → Customer → **Select customer**, then type
- **Steps:** open the picker; it lists 6 customers. Type `QA Order`.
- **Expected:** "QA Order" stays in the list.
- **Actual:**
  - "No customers found." The server action now returns the customer: the same `UserWhereInput` (`AND` of per-word `OR name/email`) gives `[{name:"QA Order"}]` via the API.
  - The cause is client-side: the combobox renders `<Command>` without `shouldFilter={false}`, and each `<CommandItem value={customer.id}>`. cmdk then filters the server results against the typed text using the **id**, so any name or email search hides every row. Typing part of a cuid would "work".
- **Fix:** `<Command shouldFilter={false}>`, or set `value` to name + email.
- **Note:** same in E-commerce. Check the address combobox and `LineItemsManager` for the same pattern.
- **File:** `features/platform/orders/components/CustomerSearchCombobox.tsx:157,173-175`.

### QA-036: Listings "Price" column is blank; virtual fields never render in any generic list
- **Area:** dashboard
- **URL:** `/dashboard/listings`
- **Steps:** open the generic Listings list.
- **Expected:** "USD 4,750.00" etc. in the new Price column.
- **Actual:**
  - The Price column is empty on all 7 rows, though the list's server action returns `"price":"USD 145.00"` and so on for each item.
  - The cause is the shared virtual-field cell. `features/dashboard/views/virtual/index.tsx:47` defines `Cell = ({ value }) => …`, but `features/dashboard/components/ListTable.tsx:166` renders `<CellComponent field={field} item={item} linkTo={…} />` and never passes `value`. So every virtual column in every list is blank.
  - The round-2 QA-027 fix therefore works only on the item page.
- **Fix:** read `item[field.path]` in the virtual `Cell`, or pass `value` from `ListTable`.
- **Note:** both files are in shared `features/dashboard` code, identical in E-commerce. Per the parity rule, fix it in E-commerce first and sync.

### QA-037: An invalid discount code dumps the raw GraphQL request and response into checkout
- **Area:** storefront
- **URL:** `/us/checkout` (or `/us/cart`) → "Gift card or discount code"
- **Steps:** with an item in the cart, enter `QA-NOPE` and click **Apply**.
- **Expected:** "That code isn't valid" (or the resolver's own "Invalid discount code: QA-NOPE").
- **Actual:**
  - A red block of text shows the full graphql-request error:
    `Unexpected error.: {"response":{"errors":[{"message":"Unexpected error.","locations":…,"path":["addDiscountToActiveCart"]}]…},"request":{"query":"\n mutation AddDiscountToActiveCart($cartId: ID!, $code: String!) {…}","variables":{"cartId":"cmvlu2jw4000dqi0164xdn3hn","code":"QA-NOPE"}}}`
  - It exposes the internal query and the cart id, and it is unreadable to a customer. Seen at 390px; same code path on desktop.
- **Cause:**
  - In production, Keystone masks resolver errors as "Unexpected error." without `extensions.originalError`.
  - `submitDiscountForm` skips the masked message, then falls back to `error.message`. graphql-request builds that message from the entire response and request.
- **Fix:**
  - Fall back to a fixed customer message.
  - Optionally map known cases (invalid, expired, already applied) to friendly text, for example from a resolver that returns a typed result instead of throwing.
- **Note:** same in E-commerce.
- **File:** `features/storefront/lib/data/cart.ts:817-827` (`submitDiscountForm` catch). The resolver is `features/keystone/mutations/addDiscountToActiveCart.ts:93`.
